What is performance testing?

Performance Testing is a subset of Performance Engineering. It is the process of evaluating a system's behaviour under various conditions — monitoring and improving key indicators such as response time, throughput, memory, and CPU utilisation.

The three objectives (the three S) of performance testing:

⚡ Speed
How fast does the system respond under normal load?
📈 Scalability
How well does performance hold as load increases?
🏔 Stability
Does the system remain reliable over time and under stress?

Phase 01 — Performance Testing Theory

7 test types
Load Testing
Simulate expected concurrent users. Validate system meets performance targets under normal load.
WHEN: before every major release
Stress Testing
Push beyond capacity limits to find the breaking point and observe failure behaviour.
WHEN: capacity planning, new infrastructure
Spike Testing
Sudden massive traffic increase — flash sales, viral events. Does the system recover?
WHEN: seasonal launches, marketing events
Endurance Testing
Sustained load over hours/days — detect memory leaks, connection pool exhaustion, degrading response times.
WHEN: overnight soak runs
Volume Testing
Large data volumes in the database — millions of records. Test query performance and pagination.
WHEN: data-heavy features, reporting APIs
Scalability Testing
Gradually increase load — measure how performance scales. Identify the scaling ceiling.
WHEN: cloud auto-scaling validation
Capacity Testing
Determine maximum users/requests the system can handle while still meeting SLAs.
WHEN: infrastructure sizing decisions
SLA, SLO & SLI
  • SLA (Service Level Agreement) — contractual commitment: "API responds in <500ms for 99% of requests"
  • SLO (Service Level Objective) — internal target, stricter than SLA: "<300ms at p95"
  • SLI (Service Level Indicator) — the measured metric: actual p95 latency from production APM
  • Error budget: 100% - SLO availability target = allowable downtime per month
  • Baseline: run performance tests against a stable build before introducing changes — this is your reference point
Test type decision matrix
  • Normal expected traffic → Load test
  • Find system limits → Stress test
  • Sudden traffic burst → Spike test
  • Long-running stability → Endurance test
  • Big data / DB queries → Volume test
  • Cloud scaling validation → Scalability test
  • Max user capacity → Capacity test

Phase 02 — Key Performance Metrics

Core metrics reference
Metric What it tells you Typical threshold
Response time (avg) Average end-to-end latency < 2s (web), < 500ms (API)
p90 / p95 / p99 Worst experience for 10%/5%/1% of users p95 < 1s is a common SLO
Throughput (RPS) Requests processed per second Target specific to load model
Error rate % of failed requests (4xx/5xx) < 1% under load, 0% at baseline
Concurrent users (VUs) Simultaneous active virtual users Match expected peak from analytics
CPU utilisation Server CPU under load < 70% sustained, < 85% peak
Memory usage Heap/RAM consumption over time Flat line = no leak; upward drift = leak
Apdex score User satisfaction index (0–1) > 0.85 acceptable, > 0.94 excellent
Why percentiles beat averages
  • Average is misleading: 100 fast requests + 1 slow request → average looks fine but 1% of users suffer
  • p95 = 95% of requests are faster than this value — use as your primary SLO metric
  • p99 = the "tail latency" — important for user-facing APIs where 1 in 100 slow requests destroys UX
  • Always report p50, p95, p99 together — never just the average
Infrastructure metrics to monitor
  • CPU: watch for sustained >70% — indicates under-provisioning
  • Memory: a steady upward trend during endurance tests = memory leak
  • DB connections: pool exhaustion causes cascading failures — set alerts
  • GC pauses (JVM): long GC pauses appear as response time spikes
  • Network I/O: bandwidth saturation causes packet loss and timeouts
  • Tools: Grafana + Prometheus, Azure Monitor, AWS CloudWatch, New Relic

Phase 03 — JMeter: Installation, GUI & First Test Plan

Core JMeter elements
  • Test Plan → Thread Group → Samplers → Listeners — understand this hierarchy first
  • Thread Group: number of threads (VUs), ramp-up period, loop count
  • HTTP Request Sampler: method, server, path, headers, body — your basic building block
  • Config Elements: HTTP Header Manager, Cookie Manager, HTTP Cache Manager
  • CSV Data Set Config: parameterise requests from a data file (usernames, tokens, IDs)
  • Timers: Constant Timer, Gaussian Random Timer — add realistic think time between requests
Assertions
  • Response Assertion: check status code, response body text, response time
  • JSON Extractor: pull a field from JSON response into a JMeter variable for chaining
  • Duration Assertion: fail the sample if response exceeds N milliseconds
  • Size Assertion: validate response body is not unexpectedly large or empty
Listeners & reporting
  • View Results Tree: debug-only — disable in actual load tests (high memory cost)
  • Summary Report: aggregated stats — avg, min, max, error%, throughput
  • Aggregate Report: adds percentiles (p50, p90, p95, p99) — prefer this over Summary
  • Response Time Graph: visualise latency over time — spot degradation patterns
  • Generate HTML Dashboard Report: jmeter -g results.jtl -o ./report — share this
Practice test plan structure
  • Scenario 1 — Load: 50 VUs, 5 min ramp-up, 10 min sustained
  • Scenario 2 — Stress: ramp 50 → 500 VUs in steps of 50, observe break point
  • Scenario 3 — Spike: 10 VUs → 300 VUs instantly → back to 10 VUs
  • Target API: JSONPlaceholder, Reqres.in, or your own staging environment

Phase 04 — JMeter Scripting & Correlation

Correlation — the most critical JMeter skill
  • Correlation = extracting dynamic values (tokens, session IDs, CSRF tokens) from responses and feeding them into subsequent requests
  • Regular Expression Extractor: extract a value using regex — e.g. extract JWT from login response body
  • JSON Path Extractor: $.access_token — cleaner than regex for JSON APIs
  • Boundary Extractor: extract between known left and right boundaries — no regex needed
  • Reference name: the JMeter variable name — use ${varName} in downstream requests
  • Test correlation works: run 2 users — each must get their own unique token
Pre / Post processors
  • JSR223 PreProcessor: run Groovy before a request — generate random data, compute HMAC, build dynamic payloads
  • JSR223 PostProcessor: parse a response, store values, trigger conditional logic
  • BeanShell (legacy): prefer JSR223/Groovy — it is compiled and significantly faster
Groovy scripting examples
// JSR223 PreProcessor — dynamic timestamp import java.time.Instant def ts = Instant.now().toEpochMilli() vars.put("timestamp", ts.toString()) // Use ${timestamp} in request body
// JSR223 PostProcessor — extract + store def resp = prev.getResponseDataAsString() def parsed = new groovy.json.JsonSlurper() .parseText(resp) vars.put("userId", parsed.id.toString()) vars.put("token", parsed.access_token)
  • Always use vars.put() to pass data to subsequent samplers
  • Use log.info() for debug output — check jmeter.log
  • Groovy is 10–50× faster than BeanShell — always prefer it

Phase 05 — Distributed & Non-GUI Testing

Non-GUI (CLI) mode — always use for real tests
  • GUI mode is for script creation only — it consumes too many resources to generate meaningful load
  • Run: jmeter -n -t test.jmx -l results.jtl -e -o ./report
  • -n = non-GUI, -t = test file, -l = results log, -e = generate report, -o = output folder
  • Override properties at runtime: -Jthreads=200 -Jduration=300
  • Parameterise test plans with ${__P(threads,50)} so CI can control load level via flags
JMeter plugins to install
  • JMeter Plugins Manager — install from jmeter-plugins.org
  • 3 Basic Graphs: Transactions/s, Response Times Over Time, Active Threads Over Time
  • Custom Thread Groups: Stepping Thread Group (gradual ramp), Ultimate Thread Group (complex shapes)
  • PerfMon: server-side CPU/memory monitoring from inside JMeter
Distributed testing
  • One controller node + N slave/agent nodes — all run the same test plan simultaneously
  • Controller aggregates all results from agents into a single report
  • Use when single machine cannot generate enough load (e.g. 10,000+ VUs)
  • BlazeMeter: cloud-hosted JMeter agents — upload your .jmx, select regions, run at scale
  • Azure Load Testing: native cloud service that runs JMeter scripts — good for Azure-hosted apps
Results analysis checklist
  • p95 response time — did it breach the SLO threshold?
  • Error rate — any errors under normal load is a defect
  • Throughput vs VU graph — does RPS grow linearly with users?
  • Memory / CPU graphs — flat lines = stable; upward drift = leak
  • Identify the knee point: where throughput plateaus but latency rises sharply

  • Use jmeter-results-analyser or a custom Python/bash script to read the JTL and exit 1 on breach

Phase 07 — k6 Fundamentals

k6 core concepts
  • k6 is code-first: tests are JavaScript (ES6) — no GUI, version-controlled alongside your app code
  • Virtual Users (VUs): each VU runs your script in a loop — simulates one concurrent user
  • Checks: assertions in k6 — check(res, {"status is 200": r => r.status === 200}) — do NOT fail the test, just count pass/fail
  • Thresholds: fail the test programmatically — http_req_duration['p(95)'] < 1000 causes non-zero exit
  • Metrics: built-in (http_req_duration, http_reqs, vus, iterations) + custom
Executor types for every test scenario
  • constant-vus: fixed VU count for a duration → baseline load test
  • ramping-vus: ramp up then down → classic load and stress test shape
  • constant-arrival-rate: fixed RPS regardless of VU count → throughput test
  • ramping-arrival-rate: ramp RPS gradually → scalability and capacity test
  • per-vu-iterations: each VU runs N iterations → soak / endurance test
k6 script anatomy
import http from 'k6/http'; import { check, sleep } from 'k6'; export const options = { scenarios: { load_test: { executor: 'ramping-vus', stages: [ { duration: '2m', target: 50 }, // ramp up { duration: '5m', target: 50 }, // sustain { duration: '1m', target: 0 }, // ramp down ], }, }, thresholds: { 'http_req_duration': ['p(95)<1000'], 'http_req_failed': ['rate<0.01' ], }, }; export default function () { const res = http.get('https://api.example.com/users'); check(res, { 'status 200': r => r.status === 200, 'body not empty': r => r.body.length > 0, }); sleep(1); }

Phase 08 — k6 Advanced Scripting

Advanced patterns
  • setup() / teardown(): run once before/after all VUs — ideal for creating test data or obtaining a shared token
  • groups(): logically name sections of a script — get per-group metrics in the report
  • SharedArray: load a CSV/JSON data file once into shared memory — all VUs read from it without duplicating data per VU
  • Custom metrics: new Counter(), new Gauge(), new Trend(), new Rate() — track anything not built-in
  • Tags: tag requests by endpoint, region, or user type — filter metrics in Grafana
Auth flow in k6
export function setup() { const res = http.post( 'https://api.example.com/auth/login', JSON.stringify({ username: 'test', password: 'pass' }), { headers: { 'Content-Type': 'application/json' } } ); return { token: res.json('access_token') }; } export default function (data) { const headers = { Authorization: `Bearer ${data.token}` }; http.get('https://api.example.com/orders', { headers }); }
Data-driven with SharedArray
import { SharedArray } from 'k6/data'; import papaparse from 'https://jslib.k6.io/papaparse/5.1.1/index.js'; const users = new SharedArray('users', function() { return papaparse.parse( open('./data/users.csv'), { header: true } ).data; }); export default function() { const user = users[__VU % users.length]; // each VU picks a different user row http.post('/login', { username: user.email }); }
